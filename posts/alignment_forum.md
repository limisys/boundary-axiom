# Alignment Forum draft

**Title:** Boundary–report identity on Moore families: a conditional result, a counterexample, and an open attribution bridge

**Abstract:** A system can compute a boundary and write a log without making the
boundary part of its organisation. This post isolates one structural condition
under which a boundary operator and a report family are not two independent
objects: the report family must be Moore (closed under arbitrary intersections).
On that class, the two determine each other; outside it, a machine-checked
counterexample shows the identity fails. I state what is proved, what is not, and
why the attribution-to-closure bridge is the next target.

---

## 1. The problem with "boundary plus log"

The ordinary architecture is:

```
state → compute boundary → write report → act
```

The report is an output. It can be stale, corrupted, or disconnected from the
boundary state, and the system can still act. The log is evidence for an
observer; it is not a condition on the system's own organisation.

The alternative is not a better log. It is to make the report a constraint on
which states the system may commit as valid. That move raises a formal question:
under what condition are the boundary operator and the report family not two
independent objects?

## 2. The formal core

Let `Ω` be a state space and `R ⊆ P(Ω)` a family of state-sets the system will
report as closed. Define

```
c_R(S) = ⋂ { T : S ⊆ T and T ∈ R }.
```

`R` is **Moore** when it is closed under arbitrary intersections.

The Lean core proves:

1. `c_R` is always a closure operator (extensive, monotone, idempotent) — no
   precondition on `R`.
2. On Moore families, `c_R = c_R'` iff `R = R'`. Boundary and report are two
   presentations of one object.
3. For a closure generated by an intervention family `I`,
   `R = Fix(c_I)` iff `c_R = c_I`. This is the joint fixed-point form, stronger
   than mutual determination.
4. Every Moore family is the fixed-point family of a closure operator
   (representation).
5. The Moore condition cannot be dropped: an explicit non-Moore family
   `R = P(Fin 2) ∖ {∅}` is not the fixed-point family of its own closure.

The v1.0 version used `UpClosed` (`∅ ∈ R`, closed under supersets). In Lean that
condition is degenerate — it forces `R = Set.univ`, so the v1.0 identity is a
tautology. The v1.1 core uses Moore and keeps the old files only as an audit.
This correction is part of the release, not a footnote.

## 3. What is new, and what is not

The Moore/closure-operator correspondence and the representation theorem are
standard. I do not claim them as new mathematics. The contribution here is:

- the operationalization of the report family as the object the system commits;
- the explicit negative control, including the v1.0 degeneration audit;
- a finite-state consistency gate (R1–R7) that tries to make the condition a
  legal transition constraint rather than an after-the-fact check;
- a public statement of the remaining gap between the attribution layer and the
  closure layer.

The gate is a reference implementation, not a production system. The Lean core
is 45 theorems/lemmas and 13 definitions; the full corpus is 56 files / 467
theorems / 90 definitions. All are 0 `sorry` / 0 custom axioms in their stated
scopes.

## 4. Why this matters for alignment

Most agent architectures treat self-monitoring as an add-on: a monitor observes
the agent and writes a report. The report can disagree with the agent's actual
state without blocking action. The Moore condition is a way to ask whether the
report is structurally part of the boundary, not an observer's annotation.

The result is conditional. It does not say that every agent has a Moore report
family, or that a deployed agent cannot bypass the gate. It says that if the
report family is Moore, then boundary and report are not separable; if it is not,
there is a precise failure mode. That is a useful target for critique: construct
a non-Moore family that nevertheless supports a non-vacuous identity, or find a
gate bypass.

## 5. The open bridge

The programme begins with an attribution presheaf `A : Caus^op → Δ²`. The core
begins with a closure operator. Nothing in the current Lean development
constructs the closure from `A`.

There is also a level mismatch: `A` is type-valued; an actual attribution field
needs a global section. The sharpness closure is point-level; the Moore
representation theorem is set-level. A bridge would need a section, a value
predicate, a path-monotonicity condition, and an alignment identity. I have
written the route assessment; it is not a proof. I would rather state the gap
than let the boundary/report result be read as having closed it.

## 6. Invitation

The most useful responses are:

- a non-Moore report family with a non-vacuous boundary–report identity;
- a concrete gate bypass: a committed bundle whose boundary and report disagree
  in a way R1–R7 do not catch;
- a derivation of the attribution bridge, or a proof that no such derivation
  exists under the programme's assumptions.
